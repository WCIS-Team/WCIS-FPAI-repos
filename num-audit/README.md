# num-audit 设计说明

交付物（方案文档、验收记录、报告）里数字错误的**外置门禁**。不是"提醒我要仔细"，
是把"仔细"变成一个会非零退出的命令。

## 更正记录（2026-10-26）

本节上一版写的是"四类错"，实际表里有五行；新增的第五类不是数字错，是**对数字的解释错**——
我说"换成只看工具入参这个口径，数字就干净了"，而两个口径跑出来是 64 与 62 条（只差 2 条）。
真正变的东西是**问的问题**：62 条是"建＋跑＋读输出"的全集，34 条是其中"写文件"的子集。
写这段解释时我没先把两个集合的定义列出来，落笔的顺序反了——结论先行、账在后。
下面「成本」一节就是按可核对的形式重写的（每个数带定义、带算式、带读数时刻）。

## 为什么会错（本工具存在的实测依据）

2026-10-25 一轮里，同一份方案文档连续出现下面这几类错，没有一类是"不会算"（表就是清单，不再在正文里写数量）：

| 错法 | 实例 | 为什么自检没拦住 |
|---|---|---|
| 印象当引用 | 写"opt_design 十次全失败"，盘上没有"十次" | 句子读起来像引用，其实是我压缩出来的计数，从没 grep 过 |
| 派生量不做除法 | "分帧额外延迟 20–60 ms"，实算 0.024 ms | 写成"量级区间"就跳过了复核 |
| 无出处基数 | 117.5 MB/s（"千兆 940 Mbps goodput"），盘上零出处 | 中间数拿来自证，闭环自洽 |
| **把对的判成错的** | 判"preamble+SFD 算了两遍"，把正确的 1474 B 改成 1466 B | "我发现了一个错"这句话自己没过算式 |
| **解释句不过账** | 说"换了统计口径所以数干净了"，实际两个口径 64 与 62 条只差 2 条 | 变的是**问的问题**不是口径；这类句子里没有算式，A1/A2 复算不到 |

第四条最关键：**纠错动作本身是新错的来源**。而触发我发现它的，正是 A1 在
`14 + 20 + 8 + 8 = 50` 上报的 FAIL——它逼我去看 §6.2，才暴露 §4.6 与 §6.2 的头
口径不一致。工具报"错"的地方不一定是文档错，但它保证**那里有一条我没对齐的账**。

## 三条口径（设计规则，不是实现细节）

1. **只复算，不判对错**。"这个数该不该是 50 B"要人定；工具只保证
   "写了 50 就必须等于它自己的加和"。
2. **裸数字要链**。数字只有三种合法身份：文内算式推出来的 / 盘上某文件的实测读数 /
   自己标的估计。A3 就是把"没有算式又没标估计"的数字挑出来——它给 WARN 不给 FAIL，
   因为这往往是 A 级读数，补个"实测"字样就过。
3. **锚点必须外部**。文中自己推的中间数不许拿来验证自己。千兆那条
   `1 Gbit/s ÷ 672 bit = 1 488 100 pps` 就是干这个的：它对不上，说明整条速率链是闭环自证。

FAIL / WARN 的分工：**FAIL＝硬错（算式不成立、文件找不到、行号越界），必须清零；
WARN＝要人眼（引用句里没有可比标识符、裸数字没标来源），逐条确认后可留。**
中文句子常常没有 ≥6 字符的 ASCII 标识符可比，所以 B 的 WARN 是常态；
确认口径就是把那个区间打印出来看（本轮 10 条全部这样过了一遍，全部引对）。

## 五项检查

| 项 | 查什么 | 红测里的实例 |
|---|---|---|
| A1 等式 | 文中 `a op b op c = N` 重算，含先乘除后加减 | `14 + 20 + 8 + 8 = 50` |
| A2 派生 | 载荷效率、加和、MB/s↔Mbps、最高包速、帧字节预算、每帧片数、攒积延迟、倍率 | 117.5 基数对不上 125；20 ms 对 0.024 ms |
| A3 裸数字 | 带单位/倍/pps 的断言，同段无算式且无"估/实测/待测"标记 | `handshakes … over 20096 ms` |
| B 引用 | "文件名:行号"／":行号-行号" 打开真文件：存在？越界？区间里有本句标识符？ | 一条指向不存在页的假引用 |
| C 锚点 | `anchors.json` 的外部常数真的被文中引用过（按主题 `only_if` 生效） | 缺 1 488 100／缺 ×8 换算 |

## 复跑

```bash
# 红测件必须 FAIL（exit 1），绿测件必须 0 FAIL（exit 0），否则工具作废
python -X utf8 repos/num-audit/num-audit.py repos/num-audit/selftest-red.md   --root S:/work/WCIS; echo "RED=$?"
python -X utf8 repos/num-audit/num-audit.py repos/num-audit/selftest-green.md --root S:/work/WCIS; echo "GREEN=$?"
# 交付物
python -X utf8 repos/num-audit/num-audit.py "<doc.md>" --root S:/work/WCIS
```

判据：**RED=1 且 GREEN=0 且交付物 FAIL=0**。本轮实跑：RED 9 FAIL／GREEN 0 FAIL／
方案文档 0 FAIL 10 WARN（WARN 已逐条人眼确认）。

## 门禁自己的错（2026-10-26）

`_eval_chain` 里除号分支只写了 `"/"`，没写 `"÷"`，于是 `a ÷ b` 落进 `else` 被当**减号**：
`9 ÷ 3 = 3` 被算成 6.0。它一直静默，是因为 A1 的等式正则要求运算符两侧是纯数字串，
文档里的除法式都长着单位（`125 MB/s ÷ 1474 B ≈ 84 803 pps`）匹配不上、由 A2 的专用公式代劳；
真正踩到的是我在本文件里写的一条无单位算式 `9.37 ÷ 28 ≈ 0.33`——**它把工具打死在自己身上**。

修法是加除号，但流程上有两条要记：

1. 先往 `selftest-green.md` 加**真值除法式**（`9 ÷ 3 = 3`），修前 GREEN 变 1、修后回 0；
   再往 `selftest-red.md` 加**假值除法式**（左边 12 ÷ 5，右边写成 3.6；真值 2.4），确认它报 FAIL。
   顺序反了就只能证明"我现在会报"，证明不了"我曾经不报"。
2. **绿测件要每种运算符各一条**：`+ − × ÷ /` 现在各有覆盖，缺哪个就是哪种算式没人守。

同类缺口还有一个：`anchors.json` 的 `only_if` 按关键词生效，不区分"这条链路的交付物"
和"只是提到这个词的说明文"。本文件与 SOP 都在举例时提了触发词的名字，C 项立刻冒出假 FAIL。
临时口径是说明文里不提触发词本身；真要修是给锚点加"文档类型"过滤，别在没需求时先写。

## 抓得住 / 抓不住

抓得住：算式与结论不符、单位换算错一个数量级、基数无出处、双重计数、
文件不存在、行号越界、核心速率链缺外部锚点。

抓不住（明确不作）：
- **口径选型**——用 1500 MTU 还是 1474、要不要含 IPG，工具按文中声明算，不替你选。
- **事实性断言**——"十次全失败"这类计数，盘上根本没有对应文件行时 B 抓不到；
  只有当我把它写成 `file.md:NNN` 才被抓。纪律因此是：**计数必须写成引用**。
- **中文句的引用对齐**——没有 ASCII 标识符时只能给人工确认。
- **解释句**——比大小、说"这两个数是包含关系"、说"换了口径所以更干净"。这类句子
  不含算式，A1/A2 无从复算，而本轮恰恰是它出过错。唯一的收口是写作约束：
  **关系类断言必须带各自的集合定义**（写成有"定义"列的表），否则不可核对。
- **读数的读数会漂**——同一份 transcript 在对话中持续变长，占比的分母不是常数
  （本轮两次快照：204 条/86.83 credits → 207 条/89.36）。百分比只在读数当刻成立，
  所以先给绝对值、再给占比，并标注读于哪一份快照。

## 成本（读于 2026-10-26，快照 207 条请求 / 89.36 credits）

按"我调工具的入参里出现 `num-audit`"计：

| 口径 | 定义 | 条数 | credits | 占该快照 |
|---|---|---|---|---|
| 1 | 整条记录里出现这个词 | 64 | 23.74 | 26.6% |
| 2 | 只在工具入参里出现（建＋跑＋读输出） | 62 | 23.21 | 26.0% |
| 3 | 口径 2 中工具名为 Write/Edit 的（真写文件） | 34 | 13.84 | 15.5% |

- 口径 3 是口径 2 的**子集**；两者差出来的 28 条／9.37 credits（算式 23.21−13.84）
  ＝跑脚本＋读它的输出，摊到每次 9.37÷28 ≈ 0.33 credits，而该快照单条请求中位数 0.356
  ⇒ **跑一次不比说一句普通话贵**，贵的是一次性建设。
- 一次全量输出 9 651 字符（其中中日韩 1 108），按 `CJK/1.2 + 非CJK/4` 估 ≈3 059 token；
  **默认模式已改为只打 FAIL 全量＋每条 WARN 一行摘要**，实跑方案文档：默认 975 字节、
  `--verbose` 11 884 字节（含 35 条 PASS）、`--json` 另存 13 339 字节全量报告。
  默认比全量省 1 − 975/11 884 ＝ **91.8%**。三种模式都验过：退出码不变（RED 现 9 FAIL，
  加了一条除号错例，见下节），且 9 条 FAIL 在默认模式下**逐条完整打印**，
  摘要只作用于 WARN，不会把硬错缩掉。
- 对照组：同轮三个数字错各自花掉 15／14／10 条请求（6.35／5.19／4.57 credits）。
  这些数同样读自会漂移的那份快照，故给条数与 credits，不把百分比当常数。

## 空格文件名只认反引号（2026-10-31 她裁定要加）

厂商那批教程正文文件名带空格（`Part 2_2 icraft tools.md`、`Part 4 性能分析及优化.md`），
`REF` 不吃空格 ⇒ 真引用被截成"最后一个空格之后"的片段、全仓找不到 ⇒ 一片假 FAIL。
现在 `REF` 的文件名部分拆成两支：**反引号内**允许空格（`[^`\n|]{1,140}?`，排除换行与
表格竖线），**反引号外**仍然一个空格都不许——这样散文里相邻两个词不会被吃成文件名。
所以引用带空格的文件名**必须整体放进一个反引号**，并尽量带上路径：同一份厂商文档
`wiki/PL/MOD/modrt/tutorial-runtime/docs/` 与 `repos/official/tutorial/icraft_tutorial/WL/`
各有一份、行号互不相同，裸文件名会按 `os.walk` 顺序解析到 `repos/` 那一份。
`selftest-red.md` 里那条空格名引用走的是"缺文件必须照样 FAIL"这一支，
`selftest-green.md` 里那条走的是"真文件必须打得开"这一支。
